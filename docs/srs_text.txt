I. Software Requirement Specification
1. Overall Requirements
1.1 Context Diagram
The Technology Products E-Commerce Website is a new software system that replaces the current fragmented sales processes on third-party e-commerce platforms and social networks for small and medium-sized laptop retail shops. The context diagram below illustrates the external entities and system interfaces for the initial releases, focusing on core shopping experiences, multi-method checkouts, and basic inventory tracking. The system is expected to evolve over several iterations, ultimately connecting to an intelligent, rule-based Chatbot suggestion system tailored for students, automated e-invoice generation via email, a comprehensive online warranty tracking system, and advanced financial analytics dashboards.

1.3.2.1 Actor Generalization Architecture 
The system utilizes the UML Generalization mechanism to establish a structured hierarchical access control system among actors, minimizing redundancy in use case associations.At the foundational layer, the User actor acts as an abstract authenticated entity that inherits from the unauthenticated Guest, ensuring that any logged-in session maintains public browsing capabilities. Moving vertically, the Customer directly inherits from the User, automatically receiving baseline profile-management privileges while extending into consumer-specific features (e.g., cart operations and checkouts).On the operational side, the Staff role inherits from the User to execute back-office operations such as order fulfillment and inventory tracking. Ultimately, the Administrator inherits directly from the Staff. This hierarchical chain implies that the Administrator implicitly possesses all operational capabilities of a Staff member, while explicitly maintaining isolated supreme privileges, including user governance, stock auditing, and AI guardrail moderations.
1.3.2.1 Use Case for Guest
 
  In the E-Commerce system, the Guest is an actor representing unauthenticated users—meaning any individual who accesses the system without an account or before logging in. This use case diagram defines the scope of public interactions available to Guests, which includes viewing informational store content, searching for components, and registering for an account to become an authenticated user. 
1.3.2.2 Use Case for Customer
 
  In the E-Commerce system, the Customer is an actor representing authenticated consumers—meaning any individual who has successfully registered a personal account and logged into the system. This use case diagram defines the scope of core post-login interactions available to Customers, which includes managing delivery addresses, controlling shopping carts, tracking orders, and consulting the integrated AI platform. Notably, the &lt;&lt;extend&gt;&gt; relationships in the diagram reflect the optional and situational behaviors of the Customer: transitioning to a complete checkout routine  is an extension triggered only when the Customer actively decides to finalize purchase metrics from the active cart interface . Similarly, filing a warranty request  extends directly from a historical order verification log , while reviewing tracking metrics  serves as an optional monitoring branch triggered only after a specific claim form has been formally submitted , rather than being a mandatory action in every standard consumer interaction session.  
1.3.2.3 Use Case for STAFF
 
In the E-Commerce system, the Staff is an actor representing internal operational employees—meaning any internal worker responsible for everyday order fulfillment, content maintenance, and inventory auditing. This use case diagram defines the scope of back-office operations available to Staff, which includes validating customer orders, examining media evidence for warranty claims, adjusting physical inventory quantities, and viewing high-level operational statistics. Notably, the two &lt;&lt;extend&gt;&gt; relationships in the diagram reflect the conditional behaviors of the Staff: reviewing and handling a customer's cancellation request  is an extension triggered only when an active order in the pending processing queue  contains an explicit cancellation flag submitted by a buyer. Similarly, choosing to forcefully hide or disable a component from public view acts as an optional extension triggered from within the active product catalog management wizard  when an item becomes discontinued or runs out of stock long-term, rather than being a mandatory action in every standard operational logging session.
1.3.2. 4 Use Case for ADMIN
 
In the E-Commerce system, the Admin is an actor representing supreme administrative managers—meaning any high-level system administrator responsible for overall system governance, operational audit tracking, and security monitoring. This use case diagram defines the scope of high-level system controls available to Admins, which includes browsing user profiles, structuring hardware categories, formally authorizing staff product mutations, tracking stock changes, handling marketing campaigns, reviewing deep business analytics, and managing chatbot frameworks. Notably, the two 
&lt;&lt;extend&gt;&gt; relationships in the diagram reflect the conditional behaviors of the Admin: altering systemic permissions is an extension triggered only when the Admin actively decides to change user privileges from within a specific account profile inside the global directory. Similarly, inspecting errors or refining underlying vector triages serves as another optional path triggered from the active AI guardrail monitor when inaccurate chatbot responses or user rating drops are detected, rather than being a mandatory action in every standard system governance session.

1. System detects that the current user is an Admin and that the claim already has an assigned staff owner. The system hides the direct action buttons (Approve, Reject, Complete) and displays a reassignment form.
2. Admin selects one of two options: Option A (Take Over) – assign the claim to themselves; or Option B (Reassign) – select another active staff member from the staff list.
3. Admin enters a reason for the reassignment and confirms the request.
4. System overwrites the claim's assigned staff with the new one and saves the reassignment event, together with the reason, in the history log. The claim's status remains unchanged. Flow returns to Step 3 (with the new ownership).

5. Requirement Appendix
5.1 Business Rules
    ID
Rule Definition
BR-01
Customers are only allowed to select a minimum of 2 and a maximum of 4 products simultaneously to use the configuration and price comparison feature.
BR-02
Product inventory quantity shall be automatically updated and deducted when an order reaches the confirmed status. 
BR-03
The system only accepts payments via the following methods: Cash on Delivery (COD), Bank Transfer
BR-04
Invoice must be automatically generated and sent via email to the customer immediately after a successful payment transaction.
BR-05
Customers are only allowed to cancel a warranty request when the request is still in an unprocessed state by the staff.
BR-06
Customers are only allowed to cancel an order if the order is still within the allowable cancellation period.
BR-07
Customers are only allowed to leave a review (5-star system) and personal comments for products they have successfully purchased.
BR-08
All online warranty requests submitted by customers must include valid evidence (images, videos, or documents).
BR-09
The management and tracking of product quantity and status (from the warehouse to the customer), as well as warranties, must be identified via Serial/IMEI codes.
BR-10
High-impact discount campaigns (Voucher Campaigns) created by staff must be approved by the Administrator (Admin) before being applied to the system.
BR-11
The application of discount codes (Vouchers/Coupons) must satisfy binding conditions including: expiration date, spending limit, usage limit, and application scope or bundle purchase conditions.
BR-12
Users who abuse the AI (spam, prompt injection, unsafe usage patterns) will be detected by the system, and the Admin has the right to disable (Block) that account's AI access.
BR-13
Passwords of all users in the system must be encrypted using the MD5 standard before being stored in the database to ensure security.
BR-14
Only the Administrator (Admin) has the authority to assign, change roles, deactivate, or reactivate user accounts (Customer, Staff, Accounter).
BR-15
A customer can submit a warranty request only for a product that belongs to their completed order, is linked to an active Warranty Policy, and is still within its warranty period. 
BR-16
Every newly submitted warranty request shall be created with the initial status PENDING. 
BR-17
Every warranty request creation, cancellation, and status transition shall be recorded in the Warranty History log together with theeeeeeeeeeeeeeeeee action performed, and timestamp. 
BR-18
A customer may view the complete information and processing history of their own warranty requests only. 
BR-19
A customer may cancel a warranty request only while its status is PENDING. Once cancelled, the request cannot be restored. 
BR-20
Warranty request status transitions shall strictly follow the workflow: PENDING → PROCESSING → APPROVED → COMPLETED, or PENDING → PROCESSING → REJECTED. Direct transitions to any other state are not permitted. 
BR-21
Staff shall provide processing remarks when approving or rejecting a warranty request. These remarks become visible to the customer after the processing result is finalized 
BR-22
Only authorized Staff members are allowed to process warranty requests and update their processing status. 
BR-23
A warranty request cannot be processed simultaneously by multiple Staff members. The system shall ensure that only one Staff member can process a request at a time. 
BR-24
A Warranty Policy must define at minimum: policy name, at least one applicable product category, warranty duration in months, and terms and conditions text.
BR-25
Disabling a Warranty Policy does not retroactively invalidate active customer warranties; existing warranties remain valid until their individually computed expiry dates.
BR-26
Revenue and Orders KPIs are computed from confirmed and completed orders only; cancelled and refunded orders are excluded from revenue totals.
BR-27
Conversion Rate is calculated using the total number of unique user sessions in the selected period as the denominator.
BR-28
An Inventory Alert is triggered when a product’s stock quantity falls below the defined low-stock threshold.
BR-29
Only approved product reviews are displayed on the public product detail page; pending, hidden, rejected, or deleted reviews must not be visible to public users. 
BR-30
Product average rating and total review count must be calculated from approved reviews only. 
BR-31
A customer can submit only one review for the same product in the same completed order. 
BR-32
Product review moderation actions such as approve, hide, or delete can only be performed by Staff or Admin accounts with review management permission. 
BR-33
Every product review moderation status change should be recorded with actor identity, action type, and timestamp. 
BR-34
Voucher code must be unique when a campaign uses a promo code. 
BR-35
Campaign start date and end date must form a valid time range, where the end date is later than the start date. 
BR-36
Discount value must be valid according to discount type: percentage discount must be greater than 0 and not exceed 100, while fixed amount discount must be greater than 0. 
BR-37
Deactivated voucher campaigns must not be applied to new checkout orders and must not modify completed historical orders. 
BR-38
Only Admin accounts with voucher campaign management permission can create, edit, view, or forcefully deactivate voucher campaigns. 
BR-39
Deleting a Warranty Policy permanently removes it along with its full change history; this action cannot be undone. 
BR-40
A footer policy's title must not be left empty when updating its content. 
BR-41
Deleting a footer policy is permanent and immediately removes it from the public site footer; this action cannot be undone. 
BR-42
Warranty request images: up to 5 files may be attached, in JPEG, PNG, JPG, or WEBP format, maximum 5MB per file. 
BR-43
Warranty request field lengths: serial number ≤ 100 characters, title ≤ 200 characters, defect description ≤ 2000 characters. 
BR-44
The warranty policy list is paginated at 5 records per page, ordered by creation time descending. 
BR-45
Footer policies are displayed in ascending display order; policies sharing the same order are shown alphabetically by title. 
BR-46
The footer policy management list is ordered by display order ascending, then by creation order 
BR-47
If a footer policy's code is left blank, the system automatically generates one from the title (uppercase, spaces replaced with underscores, non-alphanumeric characters removed).
BR-48
Changes to a footer policy's display settings take effect immediately on the public-facing site footer. 
BR-49
Each homepage section (Best-selling / New) displays a fixed number of products plus a “View all” button.
BR-50
Search matches by product name and brand, case-insensitive.
BR-51
Filters, brand tabs, and sorting work simultaneously and jointly update the “... matching products” count.
BR-52
Only products with ACTIVE status are displayed.
BR- 53
The price shown on a card is the Flash Sale price if still valid, otherwise the regular selling price.
BR-54
Only logged-in customers may place orders.
BR-55
Creating the order and deducting stock must occur within a single transaction (both succeed together or roll back).
BR-56
Delivery fields (name, phone, address) are required and must be validated on both the client and server before the order is created.
BR-57
The phone number must be in the correct format (e.g. 10 digits, numeric only) and the address must meet a minimum length.
BR-58
A payment method must be selected; for online/bank-transfer payment, the order is only created/confirmed once the payment result is valid, while COD is accepted immediately.
BR-59
A discount code / voucher only applies when valid (still active, eligible, correct type); a voucher may reduce the product amount or waive/reduce the shipping fee.
BR- 60
Only users with staff rights can access the order-management page.
BR- 61
Filtering, searching, sorting, and pagination operate simultaneously on the same set of orders.
BR-62
Each row in the list correctly reflects the current [Order].status.
